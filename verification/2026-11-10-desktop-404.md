# 2026-11-10 桌面版 `/orchestrator` 空 404：根因与加固观测

## 结论

`/orchestrator/api/*` 的空体 404 有两个可解释的根因，且都能确定性触发：

1. **取锁失败让管理前缀从未注册。** `Runtime` 在构造期先取 `stateDir` 同级的状态目录锁（`proper-lockfile`，`stale: 30_000`）。桌面实例被强杀后锁文件仍在，且运行期间每 15 秒刷新 mtime；30 秒内重启时 `lockSync` 立即抛 `ELOCKED`，`Runtime` 构造失败、`apply` reject，Cordis 回收插件 effect，`/orchestrator` 前缀从未注册，宿主 fallback 返回空体 404。这与"7 次中 4 次失败、等待更久就成功"的记录一致。
2. **Windows 上主会话的工具限制命名了不存在的 `bash`。** `src/app/sessions.ts` 把主会话限制为 `['skill', 'bash', 'read', ...]`，而当前桌面版 DSH 的全局工具是 `pwsh`（无 `bash`）。`tools.restrict()` 直接抛错，创建/恢复主会话失败，同样导致 `apply` reject 与空体 404。这一条用本单元新增的 `startup.json` 才定位到，是此前"等待 40 秒仍失败"的真正原因。

加固同时消除了这两条路径：管理前缀先挂载、初始化失败不卸载；锁竞争在 35 秒窗口内重试；失败写入 `startup.json` 并由 health / 503 报告；主会话工具限制只命名宿主实际提供的 shell。

## 加固内容

- `src/app/admin-mount.ts`、`src/app/startup.ts` 新增；`src/index.ts` 改为先挂载 `/orchestrator/api`、再取锁并构造 `Runtime`，任何初始化异常都记录阶段并 resolve，不再卸载路由。
- `acquireStateLock`：锁被占用时按 1 秒间隔重试，最长 35 秒，覆盖强杀后 30 秒的过期窗口；超时进入 `locked` 阶段并返回 503 诊断。
- 锁前移后 `Runtime` 使用传入的 `boot.lock`，避免 `Runtime extends Service` 在构造期已注册服务、失败后无法重建的问题。
- 前缀由 `/orchestrator` 收窄为 `/orchestrator/api`；回环 Host 校验移到请求期（`127.0.0.1`、`localhost`、`[::1]`），不再因 `webServer.host` 在注册期抛错。
- 运行时未就绪：`GET /orchestrator/api/health` 返回 **200** 并带 `phase`、`detail`、`error`、`stateDir`；其它接口返回 **503** `{ error, code: "startupPending", phase, detail, stateDir }`，不再是空体。
- `startup.json` 记录 `at`、`pid`、`listen`、`phase`、`detail`、`error`，上一份轮转为 `startup.prev.json`。
- 主会话工具限制只命名宿主已有的全局工具（`bash` 或 `pwsh`），`noWait` 守卫对两者同口径。
- 面板：503 `startupPending` 使用本地化启动诊断；空体 404 文案追加 `startup.json` / health 的排查入口。

## 未复现时如何证明加固有效

5 次连续启动中空体 404 的复现次数为 **0**。这不是靠"没看到"证明，而是：

1. **旧路径可确定性触发。** `tests/index.spec.ts` 注入 `ELOCKED`，断言 `apply` resolve、前缀仍注册、health 200 `phase: locked`、state 503 且带 `stateDir`；注入 `runtime.ready` reject，断言 `phase: failed` 且路由仍挂载。旧实现这两条都会 reject 并卸载路由，即空体 404。
2. **桌面每次等待都对应锁过期。** 上表 4 次等待时间与 `锁 mtime + 30 秒` 的误差均小于 1 秒（见"观测 2"），说明实例确实卡在取锁，并在锁过期后由重试接管，而不是恰好没有竞争。改动前，这些 15.9–29.9 秒的窗口正是 404 出现的位置。
3. **人为锁同样自愈。** 观测 3 中 `locked` 阶段可见，删锁后 1.2 秒内进入 `store-open`/`ready`，且 HTTP 从未返回空体 404。
4. **诊断契约有单测。** `tests/http.spec.ts` 覆盖无运行时 health 200 / 其它 503、`[::1]` 回环、仅注册 `/orchestrator/api`；`tests/client.spec.tsx` 覆盖 503 `startupPending` 的本地化文案；`tests/startup.spec.ts` 覆盖启动记录轮转与锁重试。
5. **第二个根因有桌面现场记录。** 修正前 health 明确给出 `tools.restrict() names unknown global tool "bash"` 与当前全局工具列表（含 `pwsh`），修正后同机零等待达到 `ready`。

## 观测边界（如实说明）

- 锁等待期间桌面进程尚未公布 Web URL，自动化探测拿不到端口；`locked` 阶段以 `startup.json` 的 `phase` 与文件 mtime 为准，首次 HTTP 响应出现在 Web 服务可用之后。因此上表 HTTP 列记录的是可用后的最终状态，阶段时间线来自启动记录。
- 本单元自动化**未截图**侧栏。侧栏由客户端 bundle 独立加载，本单元没有改动其加载路径；`lib/client.js` 的构建随 `pnpm build` 一并产出。侧栏是否显示不作为本单元的断言，已由 5 次启动中宿主正常打开页面间接覆盖。
- 观测 2 中 #3、#4 的启动器进程在结束时报告 `exited: true`，但随后 health 200、`startup.json` 为 `ready`、锁 mtime 持续刷新，说明应用由新的进程继续运行（单实例接管），不影响结论。
- `startup.json` 由多个进程写入时为 last-wins；每次记录带 `pid` 与 `at`，便于区分。
