对于每个更改 UI 的工单，PR 描述必须同时包含 Before 和 After 视觉证据，清楚标注，并标明基线和变更后的修订。捕获相同的场景、视口、主题和相关 UI 状态，使对比有意义；截图或演示都可以。仅有 After 的证据是不完整的。使用真实的应用截图，而不是把原型图当作先前的实现，也不要暴露私密的飞书内容或凭据。当后续 UI 变更使对比过时时，刷新对比。如果无法获得真实的基线截图，如实说明缺失的证据和限制，保持交接不完整，不要声称 UI PR 已就绪。worker 捕获并验证对比；主 Session 在投递 ready 结果前检查所报告的证据。

请求匹配规则、任务分派、这些提示词或仓库说明要求的审查。绝不要以 agent 账户启用自动合并，以免 agent 合并自己的工作：只用本节指定的合并 CLI 启用，即 `<merge CLI> pr merge <number> --auto --merge --match-head-commit <sha> --repo <OWNER>/<REPO>`。当本节没有指定合并 CLI 时，由人合并每个 PR。有合并 CLI 时，对于你从工单分支打开的 PR 的头提交，在以下全部成立时启用自动合并：PR 已就绪；改动少于 200 行（新增数加删除数）；这些说明要求的每个批准都覆盖该提交；并且如果它改变用户可见内容，这些说明指定了谁批准此类变更且该批准覆盖该提交。报告 ready 而无需等待批准，并在批准到达时启用自动合并。否则由人合并 PR；在你的报告中说明这一点。一旦其中任何条件不再成立（例如审查要求更改），以及在推送到 PR 之前，用 `<merge CLI> pr merge <number> --disable-auto --repo <OWNER>/<REPO>` 撤回自动合并；在新头提交满足条件后再启用。绝不要代表审查者批准或合并。

**评审者记功。** 为人工评审者记功（重写分支提交、追加 `Co-authored-by` 尾注并强推）与审查线程处置的完整流程在 dsh-superagent-review 技能中；首次评估人工评审者的反馈时先打开它。如果有人在处理同一问题，且其分支或 PR 包含本工单的代码（来自工单分支的提交，或其变更被带过来），立即用 gh 关闭本工单的 PR，无需询问任何人，并在其上留一句话指明该人的 PR。仅相关、或不包含工单代码的工作不是关闭的理由。关闭 PR 不会结束工单：用 `orchestrator_report` 报告处理结果。
