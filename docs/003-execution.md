# 003 执行

本文档跟踪一个已接受的工单如何经过执行、交付和恢复。它建立在 [001 领域模型](001-domain.md) 和 [002 授权](002-authorization.md) 之上。

## 工单阶段

每个打开的工单只有一个阶段，由它正在等待什么决定。从上到下读取表格；第一个匹配的行胜出。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| person / delivery | 向执行器会话投递输入失败；2 秒后重试，之后延迟翻倍直到一分钟，成功、新派工或工单结束会清除它 | 输入未送达 |
| person / answer | 有待人工决定 | 等待回答 |
| person / review | 最新报告是 `ready` | 等待评审 |
| person / blocked, failed | 最新报告是 `blocked` 或 `failed`，且此后没有人的消息抵达工单 | 受阻 · 失败 |
| working / queued | 没有派工，或派工待启动 | 已排队 |
| idle | 最新报告是 `waiting`，或派工已结束 | 等待触发器 |
| working | 其他所有情况 | 工作中 |

`person` 阶段表示工单没有人的输入就无法继续。新的人的消息会把 `blocked` 或 `failed` 的工单释放给其执行器，因此它移动到下一个匹配的阶段，通常是 `working`。

`idle` 工单已完成本轮，且没有未决问题。已订阅线程上的触发器可以继续它。

## 执行器

每个工单得到一个名为 `worker-<ticket id>` 的执行器会话，以及一个以工单短名命名的目录。目录在配置的执行根目录下创建，默认是 `<stateDir>/work`。

执行器会话以操作者的操作系统用户身份运行命令，无需批准。其 `dsh-superagent-worker` 预设包含工作所需的工具，并在 5 秒后把前台 shell 命令转为后台任务。这样执行器可以在下一步接收新消息，而不必等待长命令完成。

主会话使用 `dsh-superagent-router`，具有相同的 5 秒 shell 和任务等待限制，以及更小的路由工具集。会话保留创建时选定的预设。执行器子代理使用 DeepSeek Harness 的 `standard` 预设。

### 后台工作与执行器槽位

当回合结束时仍有 shell 任务或子代理在运行，工单会保留其执行器槽位并保持工作中。它不会被报告为等待，主会话也不会收到等待报告。任务或子代理完成后会在同一槽位中用结果唤醒执行器。一旦回合结束且没有后台工作，执行器会正常报告等待。

每个回合结束后，后台工作最多有 30 分钟完成。到达该限制时，shell 任务被终止，工单报告为等待。报告包含执行器的最后发言，以及哪些任务被终止或哪些子代理仍活跃。子代理允许继续。执行器在下一回合读取被终止任务的结果。

移交给会立即释放槽位，并保留报告生效。这适用于 `ready` 报告或问题之后（除非此后又收到其他输入），以及任何 `blocked` 或 `failed` 报告之后。

移交时子代理停止。shell 任务（例如为评审提供的服务器）可以继续，直到派工结束。它们不占槽位，也不受 30 分钟限制，之后的回合也是如此。它们的完成不会唤醒执行器；执行器在下一回合读取结果。

人也可以直接在执行器会话中写作来启动回合。其后台工作遵循相同规则。

派工结束时，其 shell 任务被终止且不唤醒会话。其子代理被释放，它们唤醒的任何完成回合都会被丢弃。替代派工及其等待中的输入会在关闭完成后启动。

在 DeepSeek Harness 进程内停止或重启插件走相同的关闭路径。尚未被纳入会话历史的输入会保留。关闭时为每个执行器的后台工作最多等待 10 秒；进程重启会直接结束这些工作。忙碌时被中断的派工会带恢复备注重新启动。

执行器子代理（包括嵌套的）使用 DeepSeek Harness 的 `standard` 预设，并具有执行器的权限。它们只保留执行器允许的工作工具，并在工单结束时失去这些工具。在 `standard` 下，shell 命令在 60 秒后转入后台。子代理结束时，其任务会被终止。

### 准备工单目录

在第一次派工之前，如果工单目录不存在，准备命令会在执行根目录下用 `sh` 运行一次。它有十分钟完成。没有准备命令时，执行器从空目录开始。

命令失败会使工单失败并记录其输出。重试或人在工单某个线程上的消息会再次尝试准备。典型的命令用 `git worktree` 创建检出。拉取请求分支的最后路径段与工单短名匹配时，该拉取请求属于该工单。

### 并发

工单从启动开始（包括准备）或从唤醒其空闲执行器的投递开始持有执行器槽位。它在整个活跃回合期间也持有该槽位。

配置的并发限制作用于这些槽位，另有一个额外槽位供人的消息或状态请求使用。正常槽位已满时，这类唤醒可以使用额外槽位，并在新启动之前占用下一个空闲槽位。因此新工作无法阻止人继续已有工单。

其他输入（例如 CI 结果）等待正常槽位。启动在 `working / queued` 中等待，直到有槽位空闲。启动并发运行，因此缓慢的准备命令只延迟自己的工单。

### 执行变量

准备命令和执行器指令收到相同的执行变量。命令读取环境变量；执行器在其提示词中读取它们的值和说明。它们都不包含凭据。

| 变量 | 注册者 | 值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`, `DSH_SUPERAGENT_NAME`, `DSH_SUPERAGENT_TICKET` | 执行器 | 工单的目录、短名和 id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 执行器 | 执行器不得运行的命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | 来源监听的仓库，`owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`, `DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | 智能体账号及其提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`, `DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 启动工单的 Issue 或拉取请求，以及当它是拉取请求时其 head ref |
| `DSH_SUPERAGENT_FEISHU_BOT`, `DSH_SUPERAGENT_FEISHU_CHAT` | 飞书 | 机器人，以及启动工单的群 |

工单专属值来自其目录和起始触发器。其他值来自当前部署设置。只有面板能更改执行环境设置；发给主会话的文本无法更改已配置的 shell 命令。

执行器通过智能体账号的 `gh` 访问 GitHub，通过机器人的 `lark-cli` 访问飞书。被阻止的命令按名称调用时会失败。

这些包装脚本和目录建立的是默认值，不是安全边界。执行器仍然可以通过绝对路径执行程序。

## 合并

自动合并由 **交付要求** 提示词控制。宿主没有针对合并的决策逻辑。

默认情况下，执行器绝不以智能体账号启用自动合并：GitHub 会把合并归因于启用者。交付要求必须指定另一个账号的 CLI 用于合并。没有指定时，由人来合并拉取请求。

默认指令只允许为工单打开的拉取请求启用自动合并，条件是它已就绪、所需批准覆盖 head 提交，且新增加删除少于 200 行。推送下一个修订之前，执行器会撤回自动合并。

无正文的评审（例如批准）也会作为触发器到达，并能唤醒等待评审的执行器。这些指令约束的是智能体，而不是 GitHub 的合并规则。要强制批准，请在分支保护中要求批准并忽略过时批准。省略合并 CLI 或删除自动合并且落即可要求手动合并。

## 工单如何结束

- **就绪但没有拉取请求：** `ready` 报告会以完成状态结束工单。
- **无事可做：** 执行器找不到需要人处理的工作时（例如请求无法复现或已被取代），报告 `dropped`。工单会不发消息地结束，除非匹配规则要求发一条；之后人在其线程上的消息会恢复它。
### 拉取请求

执行器报告工单起始所在的拉取请求后，工单就会关注它。由工单分支打开的每个拉取请求，在执行器报告或 GitHub 来源发现后，也会被关注。重新打开的拉取请求会再次被关注。

当工单打开的拉取请求都不再打开时，工单完成。如果它没有打开任何拉取请求，则它关注的所有拉取请求都必须已关闭。随后工单以最后一次相关关闭的结果结束，并保留其订阅，允许之后的人的评论恢复它。

恢复、重试或恢复中的工作尚未完成时，关闭不会结束工单。如果执行器确认或回答了它拥有的跟进，但此后还没有做出非进展报告，或在读取该消息后结束回合，关闭也会等待。之后的 `ready` 报告会在满足相同的拉取请求完成规则后结束工单。

聊天渠道会收到一条关于拉取请求结果的最终通知。GitHub 已经在拉取请求上显示结果。取消工单对拉取请求的订阅也会阻止它继续关注该拉取请求。

因此，“等待评审”意味着带拉取请求的 `ready` 报告。

### 跟进与上下文线程

执行器决定其工单自己线程上的人的跟进。它处理范围内的请求，并交回超出范围或属于另一个工单的请求。一旦没有执行器拥有该消息，它就成为主会话的候选。否则主会话只能按人的要求停止工作来处理该跟进。

会话把输入纳入某个步骤并随后报告或结束回合后，该输入算作已读。工单结束时，未被确认、回答或交回的未读消息返回评估，如 [002 授权](002-authorization.md) 所述。已读但未处理的消息（例如感谢）不会返回。

仅因上下文而关注的线程仍会投递消息，但不赋予工单对人工跟进的所有权，也不会恢复已结束的工单。这些消息可以被独立评估。

存活工单订阅期间，来源会轮询已订阅线程；在最后一次触发器与订阅工单结束两者中较晚者之后的两周内也会轮询。之后，消息只通过普通入口到达：GitHub 通知或飞书实时事件。

## 失败与恢复

### 执行器受阻或失败

当执行器会话报告 `blocked` 或 `failed`，或启动失败或出错（记录为 `failed`）时，工单不接受任何自动输入。

模型提供方或网络的瞬时失败、HTTP 408、429 或 5xx，或被拒绝、重置、超时的连接，会先重试三次，退避逐渐增长：启动会再次运行，回合失败的执行器会被要求继续；失败的准备命令不会重试。

一旦失败，CI 和机器人消息会记录在工单上，但不会投递，也不会唤醒会话。

其工具保持可用，因此人可以直接在会话中继续。

失败的启动不会自行重试。

人的消息、之后既不是 `blocked` 也不是 `failed` 的报告，或重试，都会结束这种保持状态。

该状态由存储的报告和输入推导出来，因此重启后仍保留。
### 重试

当打开的工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用：新派工会重新启动其执行器并接收等待中的输入，是每种情况的补救措施。

一旦人的消息抵达受阻或失败的工单，执行器就拥有该消息，因此工单显示为工作中，或在失败的启动重新开始时显示为已排队，并且不提供重试，除非投递该消息失败。

重试会结束当前派工，并在同一执行器会话、目录、分支和拉取请求中启动新的派工。

执行器模型只在创建会话时应用；已有会话保留其模型。
### 重启

运行中的派工会以“host restarted”结束，新派工会带恢复备注启动，告诉执行器在重复任何外部操作之前检查其目录、git 历史和 GitHub，最旧的工单优先。

等待、就绪、受阻或失败的派工保持原样，除非在该报告之后有输入抵达，这种情况下它们也会重新启动。

会话、目录、订阅、待处理消息和下面描述的已存储工作都能在重启后存活；每个执行器会话纳入历史的记录也是如此——步骤在认领消息后、模型调用前记录，重启截断的回合所纳入的消息在随后出现报告或回合结束算作已读，而步骤已认领但被取消或错误在进入历史前截断的消息算作未读。

重试或重启会让新派工再次收到投递给它所替代派工、且其执行器会话未纳入的消息——取消或截断的步骤可能已丢弃它们；仍留在会话中的副本（由重启保留或跨崩溃持久化）会在新派工的第一条消息之前取出，因此新的投递是唯一副本。
### 已存储的工作

dsh-superagent 在决定之后要做的事，例如把候选、跟进或报告中继给主会话、启动派工或投递输入，会先存储，然后执行。

中继或投递失败（例如无法访问其会话）时，2 秒后重试，之后延迟翻倍直到一分钟；启动失败会使工单失败，除非是上面所述的瞬时失败。

每种工作在连续三项失败后才会在概览的系统问题中报告错误；输入投递失败则显示在其工单上。

发往主会话的中继保持顺序，通知也是如此；失败的一项会挡住同类后续项。
### 来源失败

GitHub 来源独立读取每个 Issue、拉取请求和线程：读取失败会把错误留在其线程上，下次轮询时再次读取，并计入来源错误；默认连续三次轮询失败后报告来源错误；任何成功的轮询都会重置计数。

智能体失去私有仓库访问权限时，GitHub 也会返回 404，因此 404 会重试。

一个已通知的 Issue 或拉取请求如果读取持续失败，会在首次读取失败一天后丢弃；GitHub 报告其已删除时立即丢弃；此后它不再使轮询失败，其线程保留错误，来源状态会写明它。

其读取位置保持在原处，因此之后的通告或对其线程的轮询会读取失败读取所遗漏的内容。

飞书事件消费者会报告每次失败，已订阅话题的轮询会把每个失败留在其线程上。

GitHub 列表或飞书页面中格式错误的条目会被跳过，来源状态会计数。
### 渠道失败

出站消息作为已存储工作存储并发送，从 5 秒开始按退避重试，翻倍直到 300 秒。

工单发往同一对话的消息按入队顺序发出，因此其确认会先于之后的回答或结果：同一工单发往同一对话的较早消息尚未发出时，消息会等待，直到较早的消息连续失败三次并显示为问题。

其他工单的消息以及不属于任何工单的消息不会等待它。

尝试失败的消息在发出或被撤回之前一直是系统问题。

只有当来源不再监听该对话，或来源答复该对话永远无法接收时，消息才会被丢弃；来源关闭期间，它等待。

GitHub 上已删除的 Issue 或已锁定的对话，以及飞书上已撤回或飞书已找不到的消息，来源会给出该答复。

对已不存在的评审评论的回复会改发到拉取请求的对话。

被丢弃的消息保留记录，包括丢弃的时间和原因以及它所属的工单，因此它永远不会再次入队；被丢弃的确认读作已丢弃，而不是已发送。
### 暂停处理

停止派发、新评估、评估超时、输入投递和回复；已在进行中的启动会等到处理恢复。

来源继续记录触发器，运行中的执行器回合不会被打断。

人发往已结束工单的消息会等待：暂停后的第一轮会恢复该工单，前提是其授权在当时的策略下仍然成立。

进行中的评估在暂停期间不会过期；其截止时间会按暂停时长顺延。
### 无效配置

被其类型拒绝的已存储来源配置在运行时按停用处理，已保存的启用状态不变。
